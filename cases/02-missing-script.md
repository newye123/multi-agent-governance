# 案例二：一个不存在的脚本名，用两种相反的方式骗人

> 来源：真实项目的派工记录，命令与读数在 2026-10-24 重新复现验证。
> 这份案例讲的是**判据本身是错的**——而判据错的时候，「红」和「绿」都没有意义。

## 现象

任务书里写着一条判据：

```
判据：npm run test:binding-compiler 通过，退出码 0
```

执行手跑了一次，退出码非零，回报「测试红了」。

总控收到回包，判定执行手没修好，重派。

**问题是：这个脚本根本不存在。**

## 一开始以为

两个错误方向，都被踩过：

1. **执行手方向**：「我跑出来是红的，说明代码有问题」——于是去改业务代码。
2. **总控方向**：「跑出来是红的，说明执行手没干好」——于是重派。

两边都没错在自己的推理上。错在**没人去核这条命令本身是不是真的存在**。

## 取证

```bash
$ python -c "import json;p=json.load(open('package.json'));print(len(p['scripts']))"
214
```

`package.json` 里有 **214 个脚本**。名字里含 `binding` 的有三个：

```
test:assistant-binding-migration = node scripts/smoke-assistant-binding-migration.mjs
test:assistant-token-binding     = node --experimental-strip-types scripts/smoke-assistant-token-binding.mjs
test:identity-legacy-binding     = node scripts/smoke-identity-legacy-binding.mjs
```

**没有 `test:binding-compiler`。**

## 然后是最有意思的部分

同一条命令，能给出**两个方向相反**的假结果：

```bash
$ npm run test:binding-compiler
npm error Missing script: "test:binding-compiler"
$ echo $?
1
```

不接管道，退出码是 **1**。看起来像「测试失败」。

```bash
$ npm run test:binding-compiler 2>&1 | head -1
npm error Missing script: "test:binding-compiler"
$ echo $?
0
```

接了管道，`$?` 是 **0**。看起来像「测试通过」。

真相是：`$?` 拿到的是 `head` 的退出码，不是 `npm` 的。

```bash
$ npm run test:binding-compiler 2>&1 | head -1
$ echo "PIPESTATUS[0]=${PIPESTATUS[0]}  \$?=$?"
PIPESTATUS[0]=1  $?=0
```

**`PIPESTATUS[0]` 才是 npm 的真实退出码。**

对照组——一个真存在的脚本：

```bash
$ npm run test:assistant-token-binding
（正常输出）
$ echo $?
0
```

这才是「绿」的样子：脚本真的跑了，跑完了，退出码 0。

## 结论

| 问法 | 读数 | 会被误读成 |
|---|---|---|
| 不接管道 | `rc=1` | 「测试红了」→ 去改业务代码 |
| 接管道看 `$?` | `$?=0` | 「测试绿了」→ 以为修好了 |
| 看 `PIPESTATUS[0]` | `1` | 真实退出码，但仍不是「测试失败」 |
| **看命令是否存在** | **脚本不存在** | **判据错，不是执行错** |

**两个方向的假结果都不是「测试失败」。** 一个不存在的脚本，既不红也不绿——它什么都没跑。

## 代价

- 执行手被要求重做，做的是不存在的问题
- 重派一轮，编制里一个槽被占住
- 最坏的结局：如果当时接了管道，会得到 `$?=0`，于是**把一个不存在的测试记成「已通过」**，写进状态、写进发版说明

最后一种最危险，因为它连「重派」都不会触发——它会安静地通过。

## 修复：一条制度，不是一条提醒

只加一句「注意别写错脚本名」是没有用的。**要靠制度强制发现。**

复验单第 7 项：

> **任务书判据可跑吗（这一项记总控，不记执行手）**：复验手在派工前把任务书里每条判据**自己空跑一次**——脚本不存在、门数写错、期望退出码写错都算判据错。判据错时必须在回包单开一节「总控判据错」点名，附实测命令原式与真实退出码；**不得计入执行手的驳回理由**。

三个要点：

1. **核的动作发生在派工前**，不是收包后。收包后再核，一轮返工已经发生了。
2. **责任记总控**。执行手无权改判据，按错判据跑出的「红」不是他的失败。
3. **必须单开一节点名**，不能混在驳回理由里。否则下次还会有人以为「是这个执行手不行」。

同批实测还有第二例：任务书写「预检四道门」，实际是 **5 道**。同样是判据错。

## 可迁移的判据

> **判据本身也是被测对象。**

派工前问三个问题：

1. **这条命令真的存在吗？** 不是「我觉得应该有」，是 `grep` 一遍、跑一遍空跑。
2. **它的退出码是谁的？** 接了管道吗？`$?` 拿的是最后一个命令的。
3. **它失败时会不会伪装成成功？** `Missing script`、`command not found`、空文件、超时——这些都能返回 0 或非 0，取决于你怎么接。

第 3 条是通用规律：**任何「没有输出」的结果，都要先确认「是不是什么都没跑」。**

## 一条附带教训

写这份案例时，我第一次测量也错了——用了 `npm run ... | head` 然后读 `$?`，得到 `rc=0`，差点把「脚本不存在」写成「脚本通过了」。

**测量工具本身要被测量。** 这条在本仓库的另一个项目里也成立：报「0 命中」之前，先喂一条已知样本，必须被抓到，否则那个 0 是探针失灵。
