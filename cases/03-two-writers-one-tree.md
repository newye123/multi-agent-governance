# 案例三：「一槽一写者」被工具级的整册替换静默削掉

> 来源：真实多会话项目的台账事故，2026-10-24 在本机重新复现了机制本身。
> 这份案例讲的是**制度管住了人，没管住工具**——写者确实是唯一的，但工具会替他多写一次。

## 现象

追加型台账上出现过这样一幕：

```
14:35:00  某手在册尾追加了一行（760 B）
14:38:00  再读，那一行没了
```

同一时刻，这本册的属主只做过一次**改行首标记**的动作（把 `[待办]` 改成 `[已办]`），
没有删任何行，也没有回滚。

于是第一反应是：有人误删了，或者有人 `git checkout` 了。

两个方向都查了，都不成立。册子上没有删除痕迹，`git` 也没有回滚记录。

**那一行是自己消失的。**

## 一开始以为

三个错误方向，逐个被排除：

1. **「有人手滑删了」**——查了 diff，删除行数为 0。
2. **「有人回滚了文件」**——查了版本历史，中间没有旧版本被恢复。
3. **「写入被拒绝/写失败」**——写操作退出码是 0，没有报错，没有警告。

第三条最关键：**它成功了。** 成功地把别人的一行吃掉了。

## 取证

判据不是「谁改的」，而是**「这本册的 inode 换过没有」**。

对五本仍在被高频写入的活册，同拍取 `birth`（inode 出生时间）与 `mtime`（末次修改时间）：

```bash
$ stat -c '%n | birth=%w | mtime=%y | size=%s' 官制.md 待投递指令.md 心跳.log 发布进展.md
官制.md       | birth=2026-09-27 12:30:57 | mtime=2026-10-06 15:51:32 | size=460758
待投递指令.md | birth=2026-09-27 14:56:10 | mtime=2026-10-07 00:08:09 | size=...
心跳.log      | birth=2026-09-26 22:05:32 | mtime=2026-09-28 18:36:31 | size=842154
发布进展.md   | birth=2026-09-25 17:11:34 | mtime=2026-10-07 12:32:56 | size=253377
```

读数分两组，**泾渭分明**：

| 册 | birth | 当天的写入次数 | 判读 |
|---|---|---|---|
| `心跳.log` | 09-26 22:05 | 几十次 | inode 一次没换 |
| `发布进展.md` | 09-25 17:11 | 几十次 | inode 一次没换 |
| 队列册 | 09-26 22:18 | 几十次 | inode 一次没换 |
| `官制.md` | **09-27 12:30** | 几十次 | **换过一次，恰是那次整行重写** |
| `待投递指令.md` | **09-27 14:56** | 几十次 | **换过一次，恰是那次改标记** |

前三本全走脚本写，inode 稳如石头；后两本被工具改过一次，**inode 当场换新**。

**inode 的出生时间就是那次整册替换的落盘时刻**，精确到秒，能和写入动作对上。

### 现场复现

机制不是推测，本机两条命令就能复现。准备两个内容相同的文件，一个走「就地写」，一个走「写临时文件再改名」：

```bash
$ stat -c '%n inode=%i birth=%w' a.md b.md
a.md inode=61080069946383678 birth=2026-10-24 18:54:04
b.md inode=19421773393300732 birth=2026-10-24 18:54:04

# b.md：node 的 writeFileSync —— 就地截断写
$ node -e "require('fs').writeFileSync('b.md','line1\nline2\n')"

# a.md：写临时文件再 rename —— 编辑器/工具类写入的典型做法
$ node -e "const fs=require('fs');fs.writeFileSync('a.md.tmp','line1\nline2\n');fs.renameSync('a.md.tmp','a.md')"

$ stat -c '%n inode=%i birth=%w' a.md b.md
a.md inode=46443371157306339 birth=2026-10-24 18:54:06   ← 换了，birth 变成写入时刻
b.md inode=19421773393300732 birth=2026-10-24 18:54:04   ← 没换
```

**`rename` 换 inode，`writeFileSync` 不换。** 这就是全部机关。

### 丢掉的那一行是怎么丢的

```javascript
import fs from 'node:fs';
const F = 'ledger.md';
fs.writeFileSync(F, 'A\nB\nC\n');

// 手甲：读出全文（14:35:00）
const readAll = fs.readFileSync(F, 'utf8');

// 手乙：脚本通道追加一行（14:37:00）
fs.appendFileSync(F, 'D-乙追加\n');

// 手甲：把「我读到的全文 + 我的改动」整册写回（14:38:00）
fs.writeFileSync(F, readAll.replace('B', 'B-甲改'));

console.log(JSON.stringify(fs.readFileSync(F, 'utf8')));
```

真实输出：

```
落盘后全文：
"A\nB-甲改\nC\n"
乙那行还在吗 → false
```

**退出码 0，没有任何报错，乙那行没了。**

手甲做的事完全合规：他只改了自己那一行，没碰别人的内容。但他写回的是**「14:35 的全文」**，
而乙的追加发生在 14:37。中间这两分钟，被整册替换一起覆盖掉了。

## 结论

一槽一写者这条规矩本身是对的，但它守的是一个错误的东西：

| 规矩守的 | 实际发生的 |
|---|---|
| 同一时刻只有一只手在写 | 只有一只手在**写**，但工具替他写了一次**两分钟前的快照** |
| 不并发就不会覆盖 | 不并发也会覆盖——只要「读」和「写」之间隔了别人的「写」 |
| 写成功了就是写对了 | 写成功只保证「我的改动在」，不保证「别人的还在」 |

**「一槽一写者」管住了人的并发，管不住「读-改-写」这个跨时间的窗口。**

真正的危险区间不是两个进程同时跑，而是：

```
手甲读 ────────── 手甲写
         ↑
      手乙在这段时间里写了，然后被静默吃掉
```

这个窗口在工具里是**必然存在**的：工具要先把全文读进内存，改完再整篇写回。
窗口的长度等于「你思考那一段」的长度，可以是一秒，也可以是两分钟。

## 代价

- 那条 760 B 的行永久丢失，且**没有任何一方知道自己丢了东西**——丢的人不知道，被丢的人也不知道
- 台账是判据来源。少一行不报错，但下游读这本册做的判断，全部建立在不完整的册子上
- 最坏的结局不是这一行，而是这条机制会在**每一次**改行首标记时重演一遍。
  一天改十次标记，就是十次抽奖

而当时那句自查写得很诚实：

> 今日未见实际吞行（每次改后行数与邻行都核过）——**但「没吞到」是运气，不是保护。**

## 修复：换通道，不是加提醒

「下次注意」完全无效——问题不在注意力，在工具的写语义。要改的是**写通道**。

**规矩：追加型台账禁用整册替换式写入。**

- 适用范围：各类台账、心跳日志、进展册、当日记录
- 连「只改行首一个标记」也算：**标记改动同样是整册替换**
- 唯一合法通道：**同拍读 → 就地写**的脚本，且脚本必须自带两道守卫

两道守卫长这样：

```
守卫一：行数锚点
  写前记录 NR_before，写后必须 NR_after == NR_before + 预期增量
  不等 → 说明这中间册子被动过 → 拒写，重读

守卫二：邻行锚点
  写前抓目标行的上下各一行原文，写后必须逐字仍在
  不在 → 说明有人插在中间 → 拒写，重读
```

两道守卫都不能防「等长改写」（别人改了内容但行数没变），
所以兜底一条：**每 N 拍强制整篇重读一次**，N 取 6 左右。
罕见情形不因为罕见就可以不防。

同批还立了一条配套的：**判「谁动过这本册」，看 birth 不看 mtime。**
`mtime` 只能告诉你「最后一次写是什么时候」，`birth` 才告诉你「inode 被换过没有」。
后者才是「有人用了整册替换」的指纹。

## 可迁移的判据

> **并发保护要防的不是「同时」，是「读」与「写」之间的那段时间。**

三条可以直接搬走的：

1. **追加型文件，写入必须是「读-改-写」在同一个进程内完成。**
   跨进程、跨工具、跨一次人类思考，都不算。
   判据不是「有没有锁」，是**「读和写之间有没有可能被别人插入」**。

2. **判「文件被整册替换过」看 `birth`，不看 `mtime`。**
   `mtime` 推进可能只是正常追加；`birth` 变新，说明整个 inode 被换掉了，
   一定有人用了「写临时文件再改名」这条路。

3. **守卫要能自证会红。**
   写完「行数锚点」之后，先故意插一行让别人写，再跑一次守卫，**必须拒写**。
   拒不了，就等于没有守卫——这条和本仓库另外两个案例是同一个判据：
   **不会红的断言等于没有断言。**

## 一条附带教训

事故里最容易被漏掉的不是机制，是**「合规的动作造成不合规的结果」**。

手甲每一步都对：只改自己那行、改完核对行数、核对邻行、没碰别人内容、退出码 0。
他唯一做错的，是**用了一个会把两分钟前快照盖回去的通道**。

所以事后追责如果只看「谁删的」，会得出「没人删」这个结论——
然后这条机制原封不动地留着，等下一次抽奖。

**追问的方向应该是「用了什么通道」，不是「谁动了手」。**
