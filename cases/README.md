# 案例索引

三个案例，全部来自真实事故，读数在 2026-10-24 重新复现验证过。
共同点：**出事的时候，系统看起来都是正常的。**

| # | 案例 | 骗你的是什么 | 一句话判据 |
|---|---|---|---|
| 01 | [后台 Agent 被「用户插一句话」杀死](01-background-agent-killed.md) | 没有通知 | 判「挂死」看**有没有回包文件**，不看有没有响应 |
| 02 | [一个不存在的脚本名，用两种相反的方式骗人](02-missing-script.md) | 退出码 | 判据本身也是被测对象，派工前先空跑一次 |
| 03 | [「一槽一写者」被工具级的整册替换静默削掉](03-two-writers-one-tree.md) | 写成功 | 并发保护防的不是「同时」，是「读」与「写」之间那段时间 |

## 为什么是这三个

不是挑最惨的，是挑**三个不同的失败层**：

- **案例一：通知层失效。** 系统挂了，但没人被叫醒。这是治理链的断点。
- **案例二：判据层失效。** 系统没挂，是「怎么算通过」写错了。这比挂了更贵，因为它会把错的记成对的。
- **案例三：保护层失效。** 规矩写对了、也执行了，但工具在规矩之外多写了一次。这是最隐蔽的一层。

三层依次往下：**没人知道 → 知道了但判错 → 判对了但保护不住。**

## 三份案例的公共结构

每份都按同一个骨架写，不是排版偏好，是**为了让你能核**：

```
现象      —— 当时看到的是什么
一开始以为 —— 排除掉的错误方向（含为什么排除）
取证      —— 命令原式 + 真实读数
结论      —— 表格对照：「以为的」vs「实际的」
修复      —— 一条制度，不是一条提醒
可迁移的判据 —— 能搬到别的项目去的
```

「一开始以为」这一节不能省。省掉它，案例就变成「我早就知道」，
读者学不到**怎么排除**，只学到**结论长什么样**。

## 怎么用

不要通读。按症状查：

| 你现在的症状 | 看哪份 |
|---|---|
| 派出去的活没回音，不知道是慢还是死了 | 01 |
| 测试红了但看不出为什么，或者绿得可疑 | 02 |
| 台账/文档/配置文件莫名少了几行 | 03 |
| 有人在改的同一棵树，你不敢动 | 03 |

## 一个提醒

三份案例里，主角都不是「不认真的人」。

案例一里是**用户插了一句话**——完全正常的行为；
案例二里是**照着任务书跑**——完全正确的执行；
案例三里是**只改了自己那一行**——完全合规的操作。

事故不是由失误造成的，是由**正常操作碰上了一个没设防的边界**造成的。

所以修法只能是制度，不能是提醒。**「下次注意」在这三个案例里一次都没用。**
