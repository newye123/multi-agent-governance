# 编制册模板与派工算法

会话是会泄漏的资源。新建一个会话的成本接近零，回收一个会话的注意力成本接近无穷——
所以**不治理的话，会话数只增不减，且没有一个会被明确解任**。

这份文件给三样东西：一张能填的表、两个算法（派工/回收）、三条巡检命令。

---

## 一、编制册（一张表，六个字段）

```markdown
| 槽位 ID | 角色 | 写入面 | 状态 | 手上任务 | 末次活跃 |
|---|---|---|---|---|---|
| a1b2c3d4 | 户部·执行 | src/lib/server/billing/** | 在任 | FG-SKILL-07 | 10-24 14:35 |
| e5f6a7b8 | 门下·复验 | 只读 | 空置 | — | 10-24 11:02 |
| c9d0e1f2 | 工部·取证 | scripts/audit/** | 已解任 | FG-SKILL-05 | 10-23 22:10 |
```

四个字段不能省，各有各的用：

| 字段 | 为什么必须有 | 缺了会怎样 |
|---|---|---|
| **槽位 ID** | 派工时的唯一指向 | 「派给那个复验手」→ 派错人 |
| **写入面** | 撞车检测的唯一依据 | 两个槽改同一批文件，谁都不知道 |
| **状态** | 决定能否复用 | 往已解任的槽里派活，活石沉大海 |
| **末次活跃** | 回收算法的排序键 | 无法判断谁是「最老的空闲槽」 |

### 状态只有四种

```
在任     —— 手上有任务，正在跑
空置     —— 没任务，可立即复用
已解任   —— 交过包，不再接活（会话保留，历史可查）
不可达   —— 探测无响应（cold），需先复活或换槽
```

**「已解任」不是「空闲」。** 这是最容易混的一处：已解任的槽里塞新活，
它会带着上一轮的上下文和结论去干新活，而你不知道它带了什么。

### 页眉三件套

册子第一行必须是：

```markdown
> 编制上限 8 ｜ 当前 在任 __ / 空置 __ / 已解任 __ ｜ 本册末次改判：2026-10-24 14:35 ｜ 依据：__
```

改判（职责、编制、复验手、开窗依据）时，**同一轮内必须同步三处**：
① 本册页眉 ② 所有仍在跑的《任务书》页眉 ③ 指向旧会话的定时任务提示词。

实测理由：治理文档自己的页眉也是会被下游当判据用的字段，**过期即造假案**。
曾有下游据一句 3 天前的旧页眉，判定一条派工「与编制口径相撞」，实际上那条口径当天已改。

## 二、派工算法

```
输入：一个任务（写入面 W）
输出：一个槽位 ID

1. 若 W 与任何「在任」槽的写入面相交：
       → 不派。串行（等它交回包）或换树（独立 worktree + 明确基线 SHA）
       → 「边写边协调」不在选项里

2. 在「空置」槽里找写入面匹配的：
       → 找到 → 复用（优先，因为被委派轮次内建新会话的窗口不稳定）
       → 找不到 → 进 3

3. 若 在任 + 空置 < 上限 8：
       → 新建槽，登记写入面
       → 进 4

4. 若已达上限：
       → 按「末次活跃」升序，解任最老的空闲槽（不是最老的槽）
       → 腾出位置后回到 3
       → 若所有槽都在任 → 不派，排队。**不允许为赶工超编**
```

**关键点：第 1 步先于第 2 步。**
先查撞车，再找空槽。反过来的话，你会先找到一个「看起来闲着」的槽，
然后为了用上它，说服自己「写入面大概不冲突」。

**关键点：第 4 步解任的是「最老的空闲槽」，不是「最老的槽」。**
最老的槽很可能正在干最关键的活。

## 三、回收算法

一个槽什么时候回收：

| 触发 | 动作 |
|---|---|
| 交了回包并通过复验 | 状态 → 已解任，清空「手上任务」 |
| 超过约定时限无回包文件 | 判**挂死**，槽位回收，改派 chat 会话续做 |
| 连续 3 轮被驳回 | 第 4 轮换新槽（换人）+ 升级表述 |
| 第 4 轮仍不合格 | 停车上报 Owner，不再自动重派 |
| 回包写了「等用户确认」 | **当挂死处理**。worker 问了没人能答 |

最后一条要单独说：**「等用户确认」不是一种状态，是一种挂死。**
被委派的轮次里没有人在看，它等到的是超时，不是回答。
需要拍板的事项，正确做法是写进回包「开放问题」字段，让总控去拍。

### 判「挂死」看什么

不看「有没有响应」，看**「有没有回包文件」**。

理由是案例一：后台 Agent 被用户随口一句话连带杀死时，它不会发任何通知。
如果判据是「没响应」，你要等到自己想起来去问；如果判据是「回包文件不存在」，
时间一到就能判定，不需要问。

```bash
# 约定路径上没有回包文件，且已过时限 ⇒ 挂死
test -f 回收/<编号>/回包.md || echo "挂死：无回包文件"
```

## 四、巡检三命令

每轮开工前跑一遍，三个读数回答三个不同的问题。

### 1. 这棵树有没有别人的现场

```bash
git -C <树> status --porcelain
```

空 ⇒ 干净，可以开窗。
非空 ⇒ **先看是什么，再决定动不动作**。别人的未提交改动是最高危状态。

⚠️ 一个真实的坑：`porcelain` **不是恒为 0 的永真不变量**。
同一棵树上会有别的手在「应用补丁 → 跑门 → 还原」，你抓到的可能是这个循环的中间态。
判脏要看**两拍以上**，并且按文件指名，不能只报一个行数。

### 2. 最近谁在写

```bash
find <目录> -type f -newermt '-15 minutes' -not -path '*/.git/*' | head -20
```

列出近 15 分钟内被动过的文件。
如果里面有你没碰过的文件 ⇒ 有并发写者，**你的写入面判断错了**。

### 3. 这本册被整册替换过没有

```bash
stat -c '%n inode=%i birth=%w mtime=%y' <台账文件>
```

- `birth` 很新（接近末次写入时刻）⇒ **被整册替换过**，有人用了工具级写入
- `birth` 是很久以前 ⇒ 一直就地写，安全

`mtime` 只能告诉你「最后写于何时」，`birth` 才告诉你「inode 换过没有」。
后者才是整册替换的指纹。完整机制见[案例 03](../cases/03-two-writers-one-tree.md)。

## 五、一页速查

```
派工前：查撞车 → 找空槽 → 未超编？ → 写全任务书（八字段一次写全）
派工中：只派一次，不追问，不等批复
收包后：另一只手独立复跑 → 七项全过才记账
回收时：通过即解任；无回包即挂死；「等确认」也算挂死
上限时：解任最老的空闲槽，不为赶工超编
```
