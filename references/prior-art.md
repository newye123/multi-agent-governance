# 前人做过什么，以及我们故意不照抄的四条

> 这份文件的作用不是致敬，是**划清边界**：说明这套规则里哪些是借的、哪些是改的、哪些是明确拒绝的。
> 下面提到的项目，机制描述以撰写时的公开文档为准——**你要用，自己去核一遍**，不要拿这份文件当二手权威。

---

## 一、公开实现里已有的机制

### 1. 角色化 agent + 分层委派

**代表**：crewAI、AutoGen

crewAI 的核心抽象是 `role / goal / backstory` 三元组，加上 `Process.sequential` 与
`Process.hierarchical` 两种流程；hierarchical 模式下有一个 manager agent 负责把任务分给 worker，
并对结果做汇总。

AutoGen 的核心抽象是「可对话 agent」，`GroupChat` 由一个 `GroupChatManager` 决定下一个发言者，
配合 `max_consecutive_auto_reply` 防止单 agent 无限自说自话。

**我们借了什么**：角色分工、分层委派、上限控制。

**我们改了什么**：**分槽依据**。它们的槽是「角色」（researcher / coder / reviewer），
我们的槽是「写入面」（这个角色被授权改哪些路径）。角色会重叠，写入面不会。

### 2. SOP 化：把流程当代码

**代表**：MetaGPT

MetaGPT 的主张是 `Code = SOP(Team)`——把软件公司的标准作业流程编码进 agent 的协作结构，
角色（产品经理 / 架构师 / 项目经理 / 工程师 / QA）按 SOP 依次产出交付物，
共享一个 publish-subscribe 消息池。

**我们借了什么**：把「流程」当成一等公民，而不是靠 prompt 里写「请按步骤来」。

**我们改了什么**：**交接介质**。它们用共享消息池，我们用文件（任务书 + 回包）。
理由见下方「不照抄第二条」。

### 3. 并行工作树 + 子 agent

**代表**：obra/superpowers、claude-flow

superpowers 是一套面向编码 agent 的 skill 库，其中有「用 git worktree 并行开发」「子 agent 驱动开发」
「先写测试」等工作流；claude-flow 提供 swarm / hive-mind 式的编排层，
带 memory、hooks 与 queen-worker 层级。

**我们借了什么**：「并行必须换树」这一条——独立 worktree + 明确基线 SHA。
这是**物理隔离**，比任何协调协议都可靠。

**我们改了什么**：没有改，直接照抄。这是全套规则里唯一一条「照抄」的。

### 4. 门禁 / 守卫 / 预检

**代表**：几乎所有成熟工程实践，不限于 agent 领域

pre-commit hook、CI gate、release preflight、assertion guard——这套东西在 agent 出现之前就存在。

**我们借了什么**：全部。

**我们加了一条**：**守卫必须自证会红**（负控）。
一条从来没红过的断言，等于没有断言——因为你不知道它是「通过」还是「根本没跑」。
做法是注入一处已知破坏 → 守卫必须变红 → 还原 → 校验哈希一致。

## 二、三省六部：制度史里的制衡结构

### 史实骨架

三省六部制定型于隋、完善于唐：

| 机构 | 职掌 | 关键权力 |
|---|---|---|
| **中书省** | 草拟诏令 | 拟令 |
| **门下省** | 审核诏令 | **封驳**——认为不当可以驳还，诏书不下 |
| **尚书省** | 执行 | 下辖六部：吏、户、礼、兵、刑、工 |
| **御史台** | 监察 | 独立于行政系统，可直接弹劾 |
| **吏部考功司** | 官员考课 | 按政绩定升降 |

### 借的是结构，不是名词

这套结构真正可迁移的地方只有一句：

> **拟令的、批准的、执行的、记账的，必须是四只不同的手。**

具体到 agent 协作：

```
中书（总控）拟令  →  门下（复验手）封驳  →  尚书（执行手）动手  →  考功（退出码）记账
                            ↑                                          │
                            └──────────── 御史（只读监察）────────────┘
```

**为什么这一条值得从 1400 年前搬过来**：因为 agent 的默认失败模式恰好是
「拟令、执行、自评」三合一——它写方案、它改代码、它说改好了。这个组合在任何组织里都是腐败结构，
不是因为它坏，是因为**没有人有能力说「不」**。

### 我们改了什么

- **六部按写入面重划**，不是按史实职掌。史实里户部掌钱谷、刑部掌律令，我们是
  「户部 = 服务端与账务」「刑部 = 门禁与测试」。名词借了，边界重划了。
- **加了编制上限 8**。史实里的三省六部是个庞大官僚系统，我们只要 8 个槽——
  因为槽一多，就没人能说出「现在到底有几个活在跑」。
- **御史台没有写权**。史实里御史有弹劾权，我们连弹劾都没有，只有「直报 Owner」。
  给它写权，它就会开始改东西，然后它也需要被监察。

## 三、故意不照抄的四条

这四条都是主流做法，我们明确拒绝。理由都不是「不好」，是**在我们的约束下会失效**。

### 第一条：不照抄「由 LLM 自动选下一个发言者」

**出处**：AutoGen `GroupChatManager`、crewAI hierarchical 的 manager。

**主流做法**：让一个 manager agent 根据对话内容，动态决定下一步派给谁。

**为什么不抄**：

1. **选择过程不可复现。** 同一个任务跑两次，可能派给不同的槽。出了问题无法归因——
   是选择错了，还是执行错了？两个变量同时动，谁都查不出来。
2. **它会自我强化。** manager 倾向于选「上次表现好」的 agent，于是一个槽越来越忙，
   其他槽越来越闲，最后退化成单 agent 加一堆装饰。
3. **它把「写入面撞车」这个物理问题，变成了一个语义判断问题。**
   而 LLM 判断「这两个任务会不会改同一批文件」的准确率，远低于 `git status` 的准确率。

**我们改成**：静态分槽。写入面在派工那一刻就定死，由人（总控）填表决定，不由模型现场判断。
判断依据是可查的表，不是一次采样。

### 第二条：不照抄「共享消息池，agent 自由对话」

**出处**：MetaGPT 的 publish-subscribe 消息池，以及各类 multi-agent debate 框架。

**主流做法**：所有 agent 往一个共享上下文里写，互相看得到对方说了什么，多轮对话后收敛。

**为什么不抄**：

1. **上下文互相污染。** A 的一个错误假设，会被 B 当成前提继续推理，然后被 C 当成已确认事实。
   三轮之后，没人记得这个假设是谁先说的。
2. **无法界定「谁的话算数」。** 共享池里有一段话，你不知道它是「提议」「结论」还是「被推翻的旧版」。
   在文件系统里这个区分是显式的：任务书是令，回包是报，改了的代码是事实。
3. **平台硬约束**：被委派的轮次里，worker 看不到派工方的对话历史。
   共享上下文在物理上就不成立——**它看到的只有你写进任务书的东西**。

**我们改成**：文件交接。任务书一次写全（因为追加通道不可靠），回包写到约定路径。
没有共享上下文，只有两份文档和一棵树。

### 第三条：不照抄「多个 agent 投票 / 达成共识」

**出处**：各类 multi-agent debate、self-consistency 集成。

**主流做法**：让 N 个 agent 各自给结论，取多数，或辩论到收敛。

**为什么不抄**：

1. **一致同意不等于正确。** 同一个模型的多份采样，错的地方会一起错——
   这不是独立证据，是同一份偏见的 N 次重复。多数票只会让错误更自信。
2. **它把「验证」降级成了「表态」。** 复验的本意是「我自己跑一遍，看数字对不对」，
   投票的本意是「我看看别人怎么说」。后者便宜得多，也无效得多。

**我们改成**：**另一只手独立复跑**。
不是问「你觉得对不对」，是「你自己跑一次，把你拿到的退出码贴出来」。
判据是可复现的数字，不是意见分布。

判据一句话：**要复现，不要投票。**

### 第四条：不照抄「失败自动重试直到成功」

**出处**：几乎所有编排框架的 `max_iter` / `retry_until_pass` / 自动重试策略。

**主流做法**：失败了就再跑一遍，跑够 N 次或直到通过。

**为什么不抄**：

1. **这是「重试到绿」，不是修复。** 在有随机性的系统里，反复跑同一判据，
   迟早会撞上一次偶然通过。那一次会被记成「已修复」。
2. **它掩盖了「判据本身是错的」这个可能。** 一个永远不可能通过的判据，
   在重试框架里表现为「跑了很多次，很努力」，而不是「这条判据写错了」。
3. **它让失败变得廉价。** 如果失败可以自动重来，就没有人去问「为什么会失败」。

**我们改成**：**红就是红，重派要换人或升级表述。**
同槽连续 ≤3 轮，第 4 轮换新槽并升级表述，仍不合格就**停车上报**。
自动重试不在选项里——「禁止重试到绿」是考功三禁的第一条。

## 四、这套东西真正新在哪

如果只借不改，这份文件就没有存在必要。三条是我们自己长出来的：

### 1. 负控（守卫必须自证会红）

不是「跑一遍看绿不绿」，是「注入一处已知破坏，看它会不会红」。
不会红 ⇒ 这个守卫不可信，它的绿也不算数。

这条能推广到所有度量：**报「0 命中」之前，先喂一条已知样本，必须被抓到。**
抓不到，那个 0 是探针失灵，不是真的没有。

### 2. 三值退出码

`0` 通过 / `1` 有违规 / `2` 工具自己没跑起来。

第三值是关键：**没有它，「工具崩了」会被读成「检查通过」**——
因为很多工具崩溃时返回 0，或者被管道吃掉。

### 3. 「判据本身也是被测对象」

派工前，复验手要把任务书里每条判据**自己空跑一次**。
脚本不存在、门数写错、期望退出码写错，都算判据错，**责任记总控，不记执行手**。

这一条在公开框架里基本没有对应物——因为框架假设「人写的判据是对的」。
实测两例都是判据错，不是执行错。见[案例 02](../cases/02-missing-script.md)。
