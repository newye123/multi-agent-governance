# multi-agent-governance

[![tests](https://github.com/newye123/multi-agent-governance/actions/workflows/ci.yml/badge.svg)](https://github.com/newye123/multi-agent-governance/actions/workflows/ci.yml)
[![license: NC-1.0](https://img.shields.io/badge/license-NC--1.0-orange.svg)](LICENSE)

**多 agent / 多会话协作的派工与治理规则——目标只有一个：让「绿」这个字重新变得可信。**

大多数 multi-agent 的讨论在解决「怎么把活分出去」。这份东西解决的是下一层问题：
**分出去的活，回来说「做完了」，你凭什么信？**

三条不可协商的制衡：

> **拟令的不自准 ｜ 未复验不记账 ｜ 一槽一写者**

配套：任务书八字段、复验单七项、封驳五类、编制上限 8、三值退出码、负控（守卫必须自证会红）。

## 先看三个真实案例

规则是从事故里长出来的。不看案例，这套规则读起来像官僚主义。

| 案例 | 一句话 | 它证明了什么 |
|---|---|---|
| [01 后台 Agent 被「用户插一句话」杀死](cases/01-background-agent-killed.md) | 跑了 3 小时的活，用户随口一问，连人带现场一起没了，而且**不发通知** | 判「挂死」看有没有回包文件，不看有没有响应 |
| [02 一个不存在的脚本名，用两种相反的方式骗人](cases/02-missing-script.md) | 同一个命令，看 `$?` 是绿，看 `rc` 是红，两个都不是「测试失败」 | 判据本身也是被测对象，派工前先空跑一次 |
| [03 「一槽一写者」被工具级的整册替换静默削掉](cases/03-two-writers-one-tree.md) | 只改了自己那一行，别人 760 B 的行没了，退出码 0，无报错 | 并发保护防的不是「同时」，是「读」与「写」之间那段时间 |

三份案例覆盖**三个不同的失败层**：没人知道 → 知道了但判错 → 判对了但保护不住。

三份的共同点：**出事的时候，系统看起来都是正常的。**
而且主角都不是「不认真的人」——一个是用户插了句话，一个是照着任务书跑，一个是只改了自己那行。

## 它解决什么

五个真实痛点，每个都对应一条规则：

1. **派出去的活没回音。** 不知道是慢、是死、还是在等一个不会来的回答。
   → 挂死判据 = 无回包文件；「等用户确认」按挂死处理。
2. **回包说绿了，但我没法确认。** 自己跑出来的绿，写的人自己判。
   → 拟令不自准：必须由另一只手独立复跑。
3. **两个会话改同一棵树，互相覆盖。** 而且覆盖是静默的。
   → 一槽一写者 + 写入面分槽 + 台账禁整册替换。
4. **会话数只增不减。** 每个都还挂着，没一个被明确解任。
   → 常设编制 ≤8，交回包即解任，超编解任最老的空闲槽。
5. **重派三轮还是不行。** 于是开始怀疑执行手。
   → 先核判据本身：同槽 ≤3 轮，第 4 轮换人，仍不合格停车上报。

## 三条最反直觉的规则

### 1. 「一槽一写者」管得住人，管不住工具

追加型台账（台账、日志、进展册）**禁用整册替换式写入**，连「只改行首一个标记」也算。

原因是工具的写语义：它先把全文读进内存，改完再整篇写回。
**「读」和「写」之间的那段时间，别人写的东西会被一起覆盖掉，退出码 0，没有报错。**

判「这本册被整册替换过没有」看 `birth`（inode 出生时间），**不看 `mtime`**。
`mtime` 推进可能只是正常追加；`birth` 变新，说明整个 inode 被换掉了。

完整机制与现场复现见[案例 03](cases/03-two-writers-one-tree.md)。

### 2. 判「挂死」看有没有回包文件，不看有没有响应

后台 Agent 被用户随口一句话连带杀死时，**它不会发任何通知**——包括派它的那只手。

判据是「没响应」，你要等到自己想起来去问；判据是「回包文件不存在」，时间一到就能判定，不需要问。

推论：**长活、跨夜、多步骤的活只派 chat 会话，不派后台 Agent。**
判断「能不能用 Agent」的真正问题不是「活大不大」，是：**如果它中途消失，我多久会知道？**

### 3. 分槽按写入面，不按话题

话题会重叠（「这个改动既碰前端又碰门禁」），写入面不会。

按话题分槽，两个槽必然撞同一批文件；按写入面分槽，撞车在派工那一刻就能暴露。

## 它不是什么

**这不是编排框架。** 框架解决「怎么把活分出去」，这套规则解决「怎么让发出的命令可信」。
区别在于：框架默认 agent 说的是真的，这套规则默认不是。

**没有代码依赖。** 全部是规则、模板和决策树，配上 17 条自检。
（如果你要能跑的负控工具，去看同作者的 [adversarial-review](https://github.com/newye123/adversarial-review)——
那份仓库带 `negctl.py` 与 `check_report.py`，一个跑真负控、一个拒绝没有证据的审查报告。）

**不适用于**：单人单任务、无并发写、不需要第二只手判定质量的场景。

但「未复验不记账」一条仍然适用——**自己跑出来的绿，最好留一条可复跑的判据给下一个人。**

## 自检（含负控）

```bash
python -m unittest discover -s tests -v
```

17 条，六组：案例结构 / 索引 / 链接 / 脱敏 / frontmatter / 资源清单。

**守卫必须自证会红。** 本仓库的每一次提交都在 CI 里跑五次负控（注入已知破坏 → 必须变红 → 还原 → 核 sha256）：

| 负控 | 注入 | 结果 |
|---|---|---|
| 1 | 把 `## 取证` 改成 `## 取证材料（改坏了）` | 红（1 条失败） |
| 2 | 案例里塞一个禁用词 | 红（1 条失败） |
| 3 | 案例索引里的链接改错一个字符 | 红（2 条失败） |
| 4 | `SKILL.md` 资源清单漏登记一个文件 | 红（1 条失败） |
| 5 | frontmatter 去掉 `license` | 红（1 条失败 + 1 条错误） |

**第 1 次跑，负控 1 是绿的**——守卫没抓住。
根因：断言写的是 `^##\s+取证`，而 `## 取证材料（改坏了）` 以它开头，前缀命中了。
改成锚到行尾 `^##\s+取证\s*$` 之后才变红。

这就是「不会红的断言等于没有断言」的一次现场命中。完整记录见 [docs/self-check-2026-10-24.md](docs/self-check-2026-10-24.md)。
